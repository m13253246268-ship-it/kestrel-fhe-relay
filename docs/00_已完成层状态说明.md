### 4.1 NT=4 与 NT=8 的数值等价性（修正实验，已通过）

这是最后一处空白，现已闭环。**结论：位级不一致，但数值等价。**

**证据一：输入层直接解密比对（最硬的一条）**

把两份 `u0r112` 都用同一把 `sk.bin`、同一份明文参考 `.tmp_tok/tail/l0_u2_ref.bin` 解密：

| token/分量 | NT=4 谱系 `max\|err\|` | NT=8 产出 `max\|err\|` |
|---|---|---|
| t0 h0 | 3.2984e-04 | 3.2984e-04 |
| t0 h1 | 7.9285e-04 | 7.9285e-04 |
| t1 h0 | 9.8160e-04 | 9.8160e-04 |
| t1 h1 | 9.6113e-04 | 9.6113e-04 |
| t2 h0 | 1.2307e-03 | 1.2307e-03 |
| t2 h1 | 1.2706e-03 | 1.2706e-03 |
| t3 h0 | 8.7015e-04 | 8.7015e-04 |
| t3 h1 | 9.7758e-04 | 9.7758e-04 |
| **总体** | **PASS 8/8，max_err=1.2706e-03** | **PASS 8/8，max_err=1.2706e-03** |

同时两份密文的 **SHA256 8/8 全部不同**（字符面差异约 98.9%）。

也就是说：**字节完全不同的两份密文，解密回落到同一批实数槽位。**
这与 §2.4 的根因一致——线程数只改变了自举掩码（密文表示），没有改变底层明文。

**证据二：下游层消费替代输入**

用 `layver_run.ps1 -TargetLayer 1` 把 NT=8 的 `u0r112` 注入链上并跑 `lay1`：

- `RESULT=PASS`，`wall=2118s`；
- 40 项 `max|err|` 统计与 NT=4 基线**逐位相同**：
  `max=1.917E-002`、`min=1.294E-003`、`mean=8.431E-003`。

**必须写清的边界**

- 上面的等价性是**在容差口径与 `lay1` 一跳范围内**成立的，不是"全链 28 层都等价"的证明；
  噪声在多跳上的累积趋势仍需逐层盯。
- 证据一本身已足够支撑结论，且不依赖"注入是否被读到"这一细节；
  证据二作为下游交叉印证。

### 4.2 必须说清的判据边界

- `BOOT=PASS` **只代表 boot 流程（load / refresh / save）没出错，不等于数值正确**。
- 段级 `A/B/C/D` 的 `max|err| FAIL` **不是判据**：它对照的是"输入未偏离的明文参考"，
  而密文链上层间必然带偏离；归一化会把幅度拉回，最终段带 `[E2E:ref-deviate-ok]`。
- 因此"10/10 流程通过"回答的是"跑通了"；"5/5 数值通过"回答的是"算得对"。
  两者**都拿到**了，但结论仍只覆盖层 0–4。

## 5. 一个必须记录的纠错：`layver` 第一轮实验是空转

之前有一次「数值等价性验收」，结论是"`NT=8` 刷出的 `u0r112` 与 `NT=4` 基线数值等价"。
**这个结论不成立，已作废**。原因是挑错了层：

- 驱动里 `lay{L}` 读的是 `chain/u{L-1}r112`，**只有 `lay >= 1` 才走"读链上密文"分支**；
- `lay0` 走的是"明文种子加密"分支，**根本不打开任何链上密文**；
- 当时把替代 `u0r112` 注入链目录后跑的是 `T23_LAY=0`，那份密文从未被读取，
  日志里是自造密文（`[rms A] in xa np=112 xb np=112`），没有 `u0r112` 的 load；
- 因此"NEW 与 BASE 统计完全一致"只是因为两者本来就是同一次计算。

**正确做法**：要验收 `u0r112`，必须跑 `lay1`。修正实验已排队：
等归档与数值验证跑完后自动执行（用 `NT=8` 的 `u0r112` 喂 `lay1`，
与 `NT=4` 谱系的 `lay1` 基线比 `max|err|`）。

工具侧已加上保护：`tools/relay/layver_run.ps1` 现在要求 `-TargetLayer >= 1`，传 0 直接报错退出。

## 5.1 另一个必须记录的坑：`.ps1` 的"双重 BOM"让自动验证静默失败

本轮收尾时，看护脚本执行「归档 → 独立验证」两步。归档成功了，但**两次 `verify_layer` 都失败**，
报的是 PowerShell 解析错误（`赋值表达式无效 … verify_layer.ps1:19`）。

根因不是脚本逻辑，而是**文件编码**：

- `verify_layer.ps1` 开头是 `EF BB BF EF BB BF` —— **两个 BOM**；
- PowerShell 5.1 只吃第一个 BOM，第二个变成正文里的 U+FEFF，把 `param(...)` 块的解析带偏；
- 结果脚本连语法都没过，`verify_layer` 一次都没真正跑起来。

**这一类失败最危险的地方是"看起来像跑过了"**：日志文件有内容（内容是报错），
如果没有逐行看，很容易误以为"验证已完成"。

处置：

1. 把所有相关 `.ps1` 归一化成 **恰好一个 BOM**（纯 ASCII 脚本不带 BOM）；
2. 校验方式改为**模拟 PS 5.1 的真实读取路径**（有 BOM 按 UTF-8 解码，无 BOM 按 ANSI/GBK 解码）
   再试着建 scriptblock —— 这比 `Parser::ParseFile` 严格得多（后者对双重 BOM 仍然放行，
   所以之前"8/8 解析 OK"的检查是不可靠的）；
3. 修好后重跑，`lay` 与 `boot` 两种模式都拿到 `ALL_LAYERS_VERIFY_PASS`。

**教训**：工具的编码属于"交付物的一部分"。含中文的 `.ps1` 必须 UTF-8 with BOM，
且 BOM 只能有一个；否则在别人的机器上会静默失效。
